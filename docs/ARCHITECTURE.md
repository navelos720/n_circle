# ARCHITECTURE.md — System Design

## 1. Logical Architecture
```text
                   AFTER EFFECTS
                         │
                  SUITE INTEGRATION (panel + radial overlay)
                         │
             ┌───────────┴───────────┐
             │                       │
        RADIAL UI              SUITE PANEL / SETTINGS UI
             │                       │
             └──────────┬────────────┘
                        │
                 COMMAND REGISTRY (COMMAND_REGISTRY.md)
                        │
       ┌────────────────┼────────────────┐
       │                │                │
   SHORTCUTS        MENU ITEMS        EFFECTS
       │                                 │
       └───────────────┬─────────────────┘
                       │
                   AEP MANAGER (AEP_FILES.md, AEP_INJECTION.md)
                       │
                LOCAL JSON CONFIGURATION (DATA_MODEL.md, SCHEMA.md)
```
This is a logical diagram — do not treat box names as literal class/module names unless a decision record fixes them.

## 2. Layered Implementation View
1. **Presentation Layer**
   - Dockable Suite Panel: template/command browser, search, settings entry point. See `UI_LAYOUT.md`.
   - Radial Overlay: transparent, always-on-top circular menu rendered over the active AE composition window. See `WHEEL.md`.
2. **Business Logic Layer**
   - State Manager: radial menu state machine (`MOUSE_DOWN → MOUSE_MOVE → MOUSE_UP`), see `WHEEL.md` Interaction Model section.
   - Action Executor: routes the released slot to the correct handler (Command / Effect / Menu Item / AEP), see `WHEEL.md` Execution Matrix section.
3. **Data Layer**
   - `library.json`: index of all available `.aep` templates and company assets (read-mostly at runtime; generated by the dev-time indexer — `LIBRARY_INDEXING.md`).
   - `wheel_config.json`: the active user's wheel/profile configuration (read + written at runtime).
   - Both schemas are defined in `SCHEMA.md`.

## 3. Data Flow — Radial Execution
```text
1. User triggers hotkey or right-click-hold (SETTINGS.md defines the exact trigger + delay)
2. Panel/overlay renders the Radial Overlay at cursor (x, y)
3. MOUSE_MOVE computes angle via Math.atan2(dy, dx); highlights the active wedge
4. If active wedge is type "folder" and hover time > 150ms -> render outer ring
5. MOUSE_UP -> executeAction(slot) per WHEEL.md's execution matrix
6. Overlay is destroyed; the action executes through the ExtendScript bridge
```

## 4. Data Flow — AEP Template Injection
Only implement this path if `AEP_INJECTION.md` is confirmed in scope — check `project_logs/DECISIONS.md` / `project_logs/REVIEW_QUEUE.md` for the status of open question OQ-11 before building it.
```text
1. User selects a template (from the panel or the wheel)
2. Read library.json for aepFilePath / targetCompName / placeholderLayerName
3. Silently import the .aep into app.project
4. Locate the CompItem matching targetCompName
5. Create an instance of that comp, place it at app.project.activeItem.time
6. If a layer was pre-selected AND a layer named placeholderLayerName exists in the injected comp, swap its source with the pre-selected layer
7. Move imported-but-unused source items into a "Template Sources" folder in the Project panel
```

## 5. Integration Boundary Rules
- Do not choose or lock in a packaging/runtime technology that contradicts `TOOLS.md` without a new entry in `project_logs/DECISIONS.md`.
- The Command Registry (`COMMAND_REGISTRY.md`) is the single interface between the UI layer and AE-specific execution — UI components must never call `app.executeCommand()` directly; they call into the Action Executor, which is the only layer allowed to touch the ExtendScript bridge.
- Error handling flows upward from the Action Executor to a shared toast/notification component — see `ERROR_HANDLING.md`. Individual UI components do not implement their own error UI.
