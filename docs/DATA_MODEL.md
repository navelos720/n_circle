# DATA_MODEL.md — Persistence Philosophy

## Core Principles
1. Local JSON files ARE the database. No SQLite, no external database, no cloud storage of any kind.
2. **`library.json` is read-mostly at runtime.** It is generated by the dev-time indexing script (`LIBRARY_INDEXING.md`), not hand-edited by the running plugin, except via the explicit "Rebuild Index" trigger.
3. **`wheel_config.json` is read AND written at runtime** — this is where user customizations (wheel layout, profiles, settings) are persisted.
4. **Integrity / fallback**: if `wheel_config.json` is missing or fails schema validation on load, the plugin falls back to a hardcoded `default_config.json` (the company default wheel — see `INSTALLATION.md`). Never crash on a corrupted config; never silently discard user data without first attempting recovery or at minimum warning the user.
5. **Path resolution**: every path stored in either JSON file is relative to a configurable `rootPath`. The plugin resolves relative paths to absolute paths at runtime. Never hardcode an absolute path (e.g. a literal `C:/ProgramData/...` string) into application logic — `rootPath` itself is the only place such a default may appear, and it must remain user/company-configurable.
6. The storage format must stay human-readable (plain JSON, not a binary/compressed format) so it can be manually inspected or edited in an emergency, and must be validated on every load to guard against corruption.

## What Must Be Persisted (Minimum Set)
- Active wheel profile.
- Inner slot assignments.
- Outer/child slot assignments (per folder).
- AEP file references (path, display name, category).
- User-defined display labels, where the item type supports customization.
- User-selected icons/appearance, where supported.
- Relevant wheel behavior settings (activation trigger, hold delay — see `SETTINGS.md`).

Concrete JSON shapes for all of the above are defined in `SCHEMA.md`.
